# Лабораторная работа №3

**Цель работы:** создание веб-сервиса в бэкенде нашей системы для использования его в SPA.

**Порядок показа:**
1. Через Insomnia/Postman показать коллекцию 10 запросов.
2. Выполнить: GET списка услуг (с фильтром), добавить новую услугу с картинкой и видео, получить поля черновика, опубликовать услугу, получить ленту без ид, получить ленту по ид `?next=true`, поставить лайк, удалить услугу, зарегистрировать нового пользователя.
3. Показать изменённые данные через `SELECT`.
4. Объяснить модели, сериализаторы.
5. Показать функцию-singleton, где пользователь указан константой, и использование этой функции в методах.
6. Показать README с описанием методов и таблиц.

**Контрольные вопросы:** веб-сервис, REST, RPC, заголовки и методы HTTP, версии HTTP, HTTPS, OSI/ISO.

**Задание:** создание веб-сервиса со всей итоговой бизнес-логикой (кроме авторизации), подключение его к БД и тестирование в Insomnia/Postman. Для изображений услуг использовать MinIO (Silo). В README проекта описать все HTTP-методы и таблицы с их полями.

**Требования к веб-сервису:**
- Методы и URL в API соответствуют REST. Для списка услуг (как в 1 лабораторной) предусмотрена фильтрация на бэкенде.
- Взаимодействие с БД через ORM. Записи в статусе `deleted` на клиент не передаются.
- Статусы нельзя менять «с любого на любой»: у создателя два разных метода, вернуть в черновик нельзя.
- Пользователь-создатель зафиксирован во всех методах — указан константой через функцию-singleton.
- Системные поля (ид, статусы, создатель и модератор, даты создания, формирования и завершения) передавать с клиента для изменения запрещено — они вычисляются на бэкенде.
- В начале адреса каждого метода добавлен `/api`.

## Описание веб-сервиса

### HTTP-методы

Адрес сервера: `http://localhost:8080`. Все методы начинаются с `/api`. Ответ — JSON самого ресурса, без обёртки: код состояния передаётся HTTP-статусом, тело при ошибке — `{"error": "..."}`. Текущий пользователь — константа singleton `auth.CurrentUser()` (ivanov, id = 1).

**Домен услуги (ресурс `acids`):**

1. **GET /api/acids** — плитка: список опубликованных услуг с признаком `is_mine`, фильтрация на бэкенде `?min=&max=&acid_name=&acid_formula=&reaction_name=`. Тело запроса: нет. Успех: 200 + массив услуг. Ошибки: 400 — некорректные параметры фильтра.

2. **POST /api/acids** — создать черновик услуги с файлами изображения и видео. Тело запроса: `multipart/form-data` с полями `reaction_name`, `acid_name`, `acid_formula`, `molar_mass`, `concentration`, `calcium_carbonate_mass`, `description`, `image`, `video`. Успех: 201 + услуга. Ошибки: 400 — нет полей или файлов, неверный тип файла.

3. **GET /api/acids/draft** — черновик текущего пользователя, id не указывается (не более 1 записи). Тело запроса: нет. Успех: 200 + услуга. Ошибки: 404 — черновика нет.

4. **PUT /api/acids/{id}/publish** — публикация черновика, статус `draft → published`. Тело запроса: нет (поля заполняются при создании). Успех: 200 + услуга. Ошибки: 404 — услуги нет или она уже не черновик.

5. **GET /api/feed** — лента опубликованных услуг с признаком `is_liked`: без параметров — первая, `?id=X&next=true` — следующая после X (циклически). Тело запроса: нет. Успех: 200 + услуга. Ошибки: 400 — некорректный id, 404 — услуги нет.

6. **POST /api/acids/{id}/like** — лайк от текущего пользователя: 1 поставить, 0 снять. Тело запроса: JSON `{"value": 1}` или `{"value": 0}`. Успех: 200 + `{"acid_id": N, "liked": 0|1, "like_count": K}`. Ошибки: 400 — некорректный id или значение `value`.

7. **DELETE /api/acids/{id}** — удаление услуги текущего пользователя, статус меняется на `deleted` (soft delete). Тело запроса: нет. Успех: 200. Ошибки: 400 — некорректный id, 404 — услуги нет или она не принадлежит пользователю.

**Домен пользователя:**

8. **POST /api/users/register** — регистрация пользователя. Тело запроса: JSON `{"username": "...", "email": "...", "password": "..."}`. Успех: 201 + пользователь. Ошибки: 400 — пустые поля, 409 — логин/email уже занят.

9. **POST /api/users/auth** (алиас `POST /api/users/login`) — аутентификация, заглушка под лабораторную 4. Тело запроса: нет. Успех: 200.

10. **POST /api/users/logout** — деавторизация, заглушка под лабораторную 4. Тело запроса: нет. Успех: 200.

### Модель услуги в JSON

Поля JSON фиксированы: если значение пустое, поле всё равно присутствует.

```
id · reaction_name · acid_name · acid_formula
molar_mass · concentration · calcium_carbonate_mass · description
image_url · video_url · likes · creator_id · creator_name
created_at · updated_at · published_at · completed_at
```

- `creator_id` — id создателя услуги; `creator_name` — имя создателя (дополнительное поле, вложенного объекта пользователя нет).
- `likes` — количество лайков; в таблице не хранится, считается при сериализации.
- `status` — системное поле (`draft`/`published`/`deleted`), клиент не может его изменить; записи в статусе `deleted` не возвращаются.
- `user_id` клиенту не передаётся: вместо него отдаётся `creator_id`.

Эта базовая модель возвращается в ответах создания, черновика и публикации. Ещё два признака добавляются только в своих запросах и в остальных ответах отсутствуют:

- `is_mine` — только в плитке (GET /api/acids): 1, если услуга создана текущим пользователем, иначе 0.
- `is_liked` — только в ленте (GET /api/feed): 1, если текущий пользователь лайкнул эту услугу, иначе 0 (вычисляется по таблице `likes`).

Создание услуги: POST создаёт черновик (`status=draft`, файлы загружаются в MinIO, ключи сохраняются в БД), PUT `.../publish` переводит услугу в `published`. Вернуть услугу из `published` в `draft` нельзя.

### Таблицы БД

Взаимодействие с БД через ORM (GORM). Модели — `internal/models`, миграции — `AutoMigrate` при старте сервера (`internal/database`).

**`acids` — услуги**

| Поле | Тип | В JSON |
|---|---|---|
| `id` | bigint, первичный ключ, автоинкремент | `id` |
| `reaction_name` | varchar(255) | `reaction_name` |
| `acid_name` | varchar(100) | `acid_name` |
| `acid_formula` | varchar(50) | `acid_formula` |
| `molar_mass` | float | `molar_mass` |
| `concentration` | float | `concentration` |
| `calcium_carbonate_mass` | float | `calcium_carbonate_mass` |
| `description` | text | `description` |
| `status` | varchar(20), not null, по умолчанию `draft` (`draft`/`published`/`deleted`), индекс | не передаётся (системное поле) |
| `image_key` | varchar(255), ключ файла в MinIO | `image_url` (полная ссылка) |
| `video_key` | varchar(255), ключ файла в MinIO | `video_url` (полная ссылка) |
| `creator_id` | bigint, not null, индекс, внешний ключ на `users(id)` | `creator_id` |
| `moderator_id` | bigint, системное поле (0) | не передаётся |
| `created_at` | timestamptz, по умолчанию now() | `created_at` |
| `updated_at` | timestamptz, меняется при публикации и удалении | `updated_at` |
| `published_at` | timestamptz, дата формирования (публикации) | `published_at` |
| `completed_at` | timestamptz, дата завершения (удаления) | `completed_at` |

Файлы изображений и видео хранятся в MinIO (Silo) в бакете `acids` с именами `images/<unix>_<hex>.<ext>` и `videos/<unix>_<hex>.<ext>` (латиница); в БД сохраняются только ключи.

**`likes` — лайки**

| Поле | Тип | Описание |
|---|---|---|
| `id` | bigint, первичный ключ, автоинкремент | — |
| `user_id` | bigint, not null, внешний ключ на `users(id)` | кто лайкнул |
| `acid_id` | bigint, not null, внешний ключ на `acids(id)` | какая услуга |
| `created_at` | timestamptz | дата лайка |

Уникальный индекс `(user_id, acid_id)` — один пользователь не может поставить два лайка одной услуге. Количество лайков не хранится, считается `COUNT` при сериализации.

**`users` — пользователи**

| Поле | Тип | В JSON |
|---|---|---|
| `id` | bigint, первичный ключ, автоинкремент | `id` |
| `username` | varchar(50), not null, unique | `username` |
| `email` | varchar(100), not null, unique | `email` |
| `password_hash` | varchar(255), not null | не передаётся (`json:"-"`) |
| `created_at` | timestamptz | `created_at` |
| `updated_at` | timestamptz | `updated_at` |

Поле `password_hash` клиенту не отдаётся (`json:"-"`). В этой лабораторной авторизация — заглушка, поэтому создатель и текущий пользователь фиксированы константой через singleton `auth.CurrentUser()` (ivanov, id = 1), значение `creator_id` подставляется на бэкенде и с клиента не передаётся.
